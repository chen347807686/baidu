# 角色排序规则安全修复

2026-11-10。修复此前确认的“数据库默认大小写不敏感时，Admin 可匹配管理员”问题。不改变三种规范角色或账户范围策略。

## 修复

- 新增 0009，不改已执行的 0001–0008。升级先以字节比较检查现有角色，只接受 bidder/manager/admin 精确值；发现非规范值就停止，错误不包含实际角色或用户信息，不执行自动归一化。
- 用单条 ALTER 同时移除原 CHECK、将角色列固定为 utf8mb4_0900_bin NOT NULL，再建立同名 CHECK。保留字符容量和规范值，不改变用户角色数据。参考 MySQL 官方 ALTER 支持多子句及修改被 CHECK 引用列时需同语句移除约束的要求：https://dev.mysql.com/doc/refman/8.4/en/alter-table.html 。本地验证为 MySQL 8.4.13，不据此声称所有旧版本兼容。
- 共享 schema 同步目标排序规则，迁移结构对比继续覆盖该列。
- 权限策略中的所有角色判断（允许列表、竞价员、主管、管理员）显式使用相同二进制 collation。即使旧库尚未升级或存在历史非规范角色，读取策略也不会将变体解释为管理员。

## 验证

专用随机测试库默认 utf8mb4_0900_ai_ci，先升级到 0008 并成功写入 Admin，重现原 CHECK 的接受条件。新查询让规范 admin 可见未分配账户，Admin 的单列和双列查询都为空。

带非规范值时 0009 迁移拒绝，版本仍为 0008、列仍为原规则、Admin 原值不变。只对合成样本明确核对后删除歧义行，再升级到 0009，重复升级无副作用。

新约束拒绝 Admin、ADMIN、admin 尾随空格/制表符、Manager、Bidder 及全角角色，并核对实际错误码 3819。首轮测试预期 IntegrityError，但 PyMySQL 将该 CHECK 错误归类为 OperationalError；修正为核对 DBAPIError 的明确 MySQL 错误码后复测通过，没有弱化实际拒绝条件。

完整 67 passed；ruff check .、ruff format --check .（75 个文件）、mypy strict（48 个源文件）通过。其它角色范围、正式报表、导入和响应模型回归通过。现有 TestClient 弃用提示仍在。

## 本机执行与回退

本机独立 onetitle_v2_local 已从 0008 升至 0009，读回列排序规则为 utf8mb4_0900_bin。升级前后比较用户 ID/角色/启用状态完全一致，会话数量不变。没有重置密码、角色或会话，也没有操作线上服务器及旧库。

0009 downgrade 明确拒绝撤销安全约束；测试确认拒绝后版本仍为 0009。必要的代码回切应保留安全结构，再评估兼容，不以恢复漏洞作为普通回退路径。MySQL 单条 ALTER 的原子 DDL 支持不代表整个应用发布或数据备份已可自动回滚，参考：https://dev.mysql.com/doc/refman/8.4/en/atomic-ddl.html 。
