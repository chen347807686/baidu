# 投放写入性能初测与并发修复

## 实际发现与修改

显式性能测量在公共夹具创建的随机 MySQL 库运行，三个场景各十二批十行，
每批新事实键，总计 360 行，核对全部提交。原默认 REPEATABLE READ 下不同
账户并发新增触发 1213 死锁；缺失键 FOR UPDATE 间隙锁是主要嫌疑，未采集
InnoDB 死锁图，不能声称已证明全部锁链。

写入事务改用 READ COMMITTED，保留账户→来源→已有事实的行锁及版本校验，
不依赖重复读快照；同账户仍串行化。不同账户复测未再触发该死锁，不保证
未来所有工作负载都无死锁；失败仍安全返回，不新增自动重试。

批内事实查重改为一次最多十键的元组 IN 查询，读取已有记录并锁定；后续
逐行覆盖规则保留。新增十行场景 SQL 从 22 次降至 13 次，重复批从 12 次
降至 3 次（按代码路径；本次实测仅新增场景）。计数不含 commit/握手。
十行上限未放宽，没有引入大事务或跳过任何校验。

## 本机结果

本机 Windows / MySQL 8.4 / PyMySQL / 回环连接；合成短词、少量空维度、
空库开始，无生产数据量。P95 为十二次样本的最大值（nearest rank）。

| 场景 | 合并查询前行/秒 | 合并查询后行/秒 | 后 P50/P95 毫秒 |
|---|---:|---:|---:|
| 单线程同账户 | 379.0 | 529.5 | 18.19 / 24.33 |
| 四线程同账户 | 489.9 | 604.0 | 56.58 / 81.26 |
| 四线程不同账户 | 713.8 | 798.5 | 48.48 / 65.31 |

两轮均已使用 READ COMMITTED。只有少量单轮结果，缓存、机器负载与后轮同时
运行的隔离回归可能影响数字，不以此宣称固定提升比例或生产 SLA。耗时包括
输入准备、连接池等待与事务提交，未直接测锁等待。可靠收益是 SQL 次数减少。
后续要在稳定空闲环境增加重复轮次、代表性存量/长维度、更新/重复/混合场景，
再测服务器延迟与吞吐；不能由数百行推算千万级容量。
