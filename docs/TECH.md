# TECH — 投放监控看板重构技术方案

版本 v0.8 · 2026-11-10。以下为技术推荐，不是已确认选型。需求与验收见 RPD，决策见 RD 第 7 节。

## 1. 结论与依据

推荐保留 Python 业务生态，以模块化单体承载 API，前端独立构建、同域部署，长任务由独立进程执行。推荐组合：Vue 3 + TypeScript + Vite，FastAPI + Pydantic，SQLAlchemy + Alembic，PostgreSQL，数据库持久任务 + 独立 worker。Redis、Celery、分区、微服务均不作为首版默认依赖。

该推荐基于代码结构和预计的多人使用、采集与操作并行需求；真实并发、机器资源、运维能力尚未确认，未做新方案压测。若 Q4/Q6 显示单机低写入且维护资源很少，优先评估下述 SQLite 简化方案。首批只选择一种生产数据库，不承诺同时兼容两套引擎。

### 已核对的项目条件

- 业务和百度/LLM/Excel 处理均在 Python，改换语言会增加重写成本；未取得团队熟悉 Vue、React、FastAPI 的证据。
- 旧前端是大型 HTML/JS 模板，主要交互为表格、筛选、规则抽屉、批量操作和任务进度，适合组件化后台。
- 报表已有按日 SQL 聚合，但仍在 Python 拼合、过滤、二次聚合及排序分页；迁库或换 API 框架不会自动解决它。
- db.py 的连接获取混入建表/迁移/种子逻辑，需独立版本迁移，不是换连接库即可解决。
- 部署脚本是 Linux shell、cron、flock、nohup；仅能证明脚本面向 Linux，不能证明生产已具备 root、systemd 或 Docker。
- 拉数、判定、预警、拓词和外部写操作需要持久状态；旧全局字典/线程锁不适合作为跨进程共同状态。

## 2. 选型比较

| 层 | 推荐 | 保留的备选与改选条件 | 代价与边界 |
|---|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite | 维护者已有成熟 React 项目与经验时选 React + TS | Vue 是基于本项目交互的建议，不宣称团队已熟悉。需确认 Node 构建环境与浏览器目标 |
| 组件/图表 | Element Plus、统一图标集、ECharts | 已有设计系统时优先沿用；不自行造完整组件库 | 先验证表格、筛选、批量操作和抽屉；表格分页是基础，虚拟滚动按实际需要，不替代服务端分页 |
| API | FastAPI + Pydantic，薄路由/服务/数据访问分层 | 团队主要维护 Flask 且学习/交付成本更敏感时，使用新工程的模块化 Flask | 推荐因请求/响应契约、验证和文档，不因名称或宣称异步就更快。鉴权、任务、审计仍需设计 |
| 数据访问 | SQLAlchemy + Alembic；报表用 Core 或参数化 SQL，业务实体按需 ORM | 少量简单查询可保留驱动层封装，但版本迁移不可省 | 不为报表加载所有 ORM 对象。迁移在发布步骤执行，连接只获取连接；原生 SQL 与 ORM 均需权限和类型边界 |
| 数据库 | PostgreSQL，普通表+针对性索引 | SQLite 适用于单机、本地磁盘、短写事务且可控单写者、压测通过的部署 | PostgreSQL 增加服务、备份、恢复、连接池和运维成本；SQLite 简化运维但限制写并发与横向部署 |
| 任务 | 数据库任务记录 + 单独 worker，定时入口单独运行 | 多 worker/跨机器/复杂工作流成为明确需求时评估 Celery；不先引入 broker | 任务领取、租约、心跳、重试和结果仍有实现成本；不是完整消息队列的零成本替代 |
| 缓存 | 先优化 SQL；只为热点加受控缓存 | 多实例共享缓存或明确性能收益时 Redis | 持久任务、幂等与审计不依赖进程内缓存；不复制旧版多层明细缓存链 |
| 部署 | 同域静态资源+API；Linux 服务守护；worker/定时入口分开 | 有容器运维能力时 Compose；无 systemd 权限时由运维提供等价守护 | FastAPI 用 ASGI 服务；Flask 用正式 WSGI 服务；开发服务器不用于生产，不用 nohup 代替恢复机制 |
| 身份 | 明确角色/账户授权，首选受控服务端会话 | 已有企业 SSO 时接入；Redis 会话非必需 | 会话可持久化在业务库并限制期限；同域安全 Cookie、CSRF 和登录策略按认证方式设计 |

Vue 的 TypeScript 支持、Vite 构建能力、Element Plus 表格及 FastAPI 的校验/契约能力见 [Vue](https://vuejs.org/guide/typescript/overview.html)、[Vite](https://vite.dev/guide/)、[Element Plus](https://element-plus.org/en-US/component/table.html)、[FastAPI](https://fastapi.tiangolo.com/features/)。选用理由为本项目判断，不是这些文档替项目给出的性能保证。

## 3. 数据库重点评估

### 3.1 为什么长期优先推荐 PostgreSQL

新库除日报还会存账户权限、规则、任务、操作结果和审计。拉数、规则保存、任务进度与百度操作可能同时写入，客户端/服务端数据库更适合管理这些并发和集中存储需求。推荐依据是写入与运维模型，不是 2.7 GB 文件或 700 个配置账户。PostgreSQL 采用 MVCC，但同一数据上的写锁、长事务和慢 SQL 仍需治理。[官方并发说明](https://www.postgresql.org/docs/current/mvcc-intro.html)

首版建议普通表、明确唯一约束、日期/账户/对象组合索引，按真实过滤/排序查计划；不默认分区、TimescaleDB、ClickHouse、读写分离或多库分片。分区有管理和查询成本，应结合规模、访问和归档方式评估。[官方分区说明](https://www.postgresql.org/docs/current/ddl-partitioning.html)

### 3.2 SQLite 简化方案的条件

新工程使用独立 SQLite 文件，业务状态与报表均需新版结构；旧库只作为只读来源。数据库位于本机可靠磁盘，写事务短、任务写入受控，配置忙等待与重试策略并观察锁等待。WAL 可改善读写并行，但同一时刻仍只有一个写者，不能据此承诺多写并发或跨主机共享文件。[SQLite 使用边界](https://sqlite.org/whentouse.html)、[WAL](https://www.sqlite.org/wal.html)

还需 checkpoint、备份一致性与恢复验证；长读取对 WAL 增长的影响纳入测量。遇到多个服务节点、持续写锁等待、后台写入影响在线响应或恢复要求超出维护能力，改选 PostgreSQL。若两者均未按目标资源验证，不写成 SQLite 一定不行或 PostgreSQL 一定达标。

### 3.3 定稿所需证据

Q4：峰值在线、活跃账户、日期跨度、同时写任务、导出量、数据增长及延迟目标。Q6：CPU/内存/磁盘、部署权限、数据库备份责任。Q8：保留期、可接受数据丢失窗口和恢复时间。先比较预期成本和约束，开发获准后在隔离环境验证所选方案；不要求先把两套完整实现都做出来。

## 4. API 与数据访问

推荐 FastAPI 的同步端点+同步数据访问作为兼容旧同步调用的起点；确有并发等待收益的链路再使用完整异步 I/O，不在 async 函数内直接执行阻塞数据库或 HTTP 调用。线程和连接池应有界，取消页面请求不等于后台任务已停止。FastAPI 的同步/异步规则见[官方说明](https://fastapi.tiangolo.com/async/)。

Flask 备选同样可满足模块化与生产服务需求；若采用 Flask，不把请求内创建的异步任务当持久后台任务。[Flask 异步边界](https://flask.palletsprojects.com/en/stable/async-await/)、[生产部署](https://flask.palletsprojects.com/en/stable/deploying/)

SQLAlchemy 用于连接、事务和查询边界，不要求所有报表 ORM 化；Alembic 管结构版本，自动生成迁移仍须审核数据变换和回滚风险。[连接与事务](https://docs.sqlalchemy.org/en/latest/core/connections.html)、[Alembic](https://alembic.sqlalchemy.org/en/latest/)

API 明确身份/账户范围、分页/稳定排序/过滤、错误和 trace、导出与任务状态。盘点旧 65 个端点的语义，不强制保持旧端点形态。迁移模型、获取连接和初始化种子分离，不随每个请求执行 DDL。

## 5. 查询与数据模型

T1 数据及时可用；T2 权限与操作保护；T3 凭据/配置治理；T4 业务语义正确；T5 前端任务流；T6 任务可恢复；T7 数据可迁移与恢复；T8 增强可选；T9 分层性能可验证。

核心对象：用户/角色/账户/归属，投放对象与日报，规则/版本/标签/人工覆盖/否词批次，预警，拓词运行/种子/候选/评分，任务/分项结果，预览/审批/写操作/读回/审计/补偿。选用队列后再加建议实体。不加入 CRM、小时事实表或素材生成域。

- 先明确日报真实唯一键；关键词与创意用稳定 ID，搜索词保留文本与触发对象、设备等真实维度。词文本不是通用唯一 ID。
- 原 MappingResolver 的负责人、部门及业务点解析需落为可查询、可版本化的映射；决定按当前或历史生效口径，先保持可验证旧行为。
- 权限与可下推筛选在读取前落实；同一关系和条件计算总数、指标及分页，分页按业务排序+稳定次序。
- 比率由分子/分母汇总后计算，不相加或平均各行比率；零分母为空。金额建议定点十进制或整数最小单位，按百度源精度和舍入核对历史 REAL 数据。
- 列表用页大小限制与列投影，深分页是否改游标按访问模式；导出是独立路径，可分块输出但不能全量装入内存。
- 预聚合只为实际热点，明确粒度、回补/更新及对账；不以“加了物化表”验收性能。

## 6. 任务与写操作

### 6.1 可靠任务

数据库登记任务类型、账户/日期、业务幂等键、状态、计划时间、尝试次数、租约/心跳、进度和结果。API 负责提交与查状态，独立 worker 执行；单独定时入口创建日任务，Web 进程不各自启动调度。

初期单 worker 可有受限并发 I/O，数据库写入和百度配额受控。进程重启后识别租约过期的未完成任务；一般计算任务可重跑，百度写入未知结果先核对。任务机制不提供“外部执行恰好一次”保证。

Linux timer/cron 只作触发器，不用 shell 吞错代表成功。需要多节点吞吐或复杂任务编排时才评估 Celery、broker、worker 和 scheduler 的整体成本；即使使用 Celery，也要避免重复调度和重复执行。[Celery 周期任务](https://docs.celeryq.dev/en/stable/userguide/periodic-tasks.html)

### 6.2 外部写入

原 pause_keyword 和 add_negative 保留。预览快照→权限/有效期校验→人工确认→必要审批→执行→逐项读回→审计；对象变化使确认/审批失效。新增动作逐项接入，不重造覆盖百度后台的全量管理平台。

幂等需包含账户、稳定对象、动作及关键参数；超时/部分成功分别落状态。添加否词是读列表再改写的模式，需处理并发覆盖风险；数据库事务不能锁住用户在百度后台的改动，执行前后应核对并记录冲突。撤回不覆盖后续合法变更；暂停恢复也不能回补丢失流量。

审计先登记执行意图，再追加结果，避免进程在写百度后退出而没有任何本地痕迹。读回可能有延迟，需可见的待核对/重试/超时状态，不把 API 响应成功等同已核实。

## 7. 配置、缓存与前端

环境变量/密钥服务只放基础配置、密钥或密钥引用；多账户映射存引用，不在账户表内重新散存明文。规则、阈值、负责人和提示词版本属于受控运行配置。运行库/日志可存必要脱敏记录；版本仓库只含无敏感模板与清单。

缓存可先不引入；使用时限定容量、TTL 与数据/映射/规则/权限版本。公共数据缓存也须在输出前强制权限过滤；用户结果缓存避免跨范围泄露。关键幂等、会话、任务不只存在进程内字典。

前端同域部署可减少跨域配置；静态构建产物与 API 可独立更新。图标集只选一种并规范语义，组件库不决定视觉风格。筛选变化取消或忽略过期响应、保留上下文；任务使用进度轮询即可，不默认引入 WebSocket。核心表格分页与状态反馈先行，虚拟化和大图表按场景启用。

## 8. 增强解耦与效果

自动种子、建议队列、直接加词和效果评估可独立选用。队列状态与执行状态分开，不把“采纳”直接解释成“已执行”；没有选加词时不要求加词结果。建议去重含目标单元、匹配和动作参数，不能只按词文本。

次日复核执行/投放/到数状态，效果评估需 Q13 的观察期、样本与转化延迟。新增词没有自身投放前数据，不伪造前后效果；不足标观察中/数据不足，不自动改规则、否词或覆盖人工。

## 10. 线上服务器部署方案

部署目标为与旧系统共用同一台线上服务器/IP，新旧入口可以不同，不要求替换旧版完整 URL。以下 Linux 方案为推荐，操作系统和资源仍待 Q6。先确认旧服务、端口、反向代理和磁盘，不覆盖或重启旧业务服务。

- 请求入口：建议反向代理统一提供 HTTPS、前端静态文件和同域 API 转发；仅开放所需入口。数据库与任务管理入口不默认对公网开放，不能仅靠更换端口保护。
- 运行单元：API、worker 分别守护；定时入口仅一个。Vue/Vite 构建在构建环境完成，服务器提供静态产物，不要求生产机器常驻 Node 开发服务。
- 部署形式：有稳定 Docker/Compose 维护条件时，优先评估 Compose 管理 API、worker 和所选数据库；否则采用独立 Python 环境与服务器已有服务管理。两种方式择一，不能把 Docker 当已具备条件。
- 持久数据：数据库文件/数据目录、导出、受控配置和备份独立于代码版本；使用容器也不得把重要数据只放容器可写层。PostgreSQL 可本机或受管服务，按资源与备份责任选择，不默认再采购服务。
- 资源：API 与 worker 的进程数、连接池、任务并发、导出大小按实际 CPU/内存/磁盘及 Q4 限制。小服务器先控制并发，不直接照搬多进程数量。
- 升级：备份并验证恢复路径→检查版本兼容→单独执行结构迁移→启动并检查 API/worker/任务→灰度切换。不可逆结构迁移不能只靠回切镜像恢复。
- 运行保障：自动启动/重启、日志轮转、磁盘和任务失败告警、备份访问控制与恢复演练；上线前核对 HTTPS、身份权限、敏感信息和外部动作单一执行方。

该部署边界不改变 Vue/FastAPI/PostgreSQL 的推荐，也不自动引入 Redis、Celery、分区或 Kubernetes。服务器资源及维护条件不足时按第 2~3 节重新选择简化方案。


### 10.1 同机部署隔离

- 入口：推荐独立的新 API 内部端口，使用新路径或另一个对外入口访问。已有反向代理时评估复用，仅改获准路由；无代理时另定入口，不与旧服务争用监听端口。新前端及 API 统一入口路径，使用子路径时同步检查静态资源基路径、API 前缀、页面路由及 Cookie 路径。具体端口/路径不预先指定。
- 安全：同一 IP 的不同端口属于不同浏览器源，但 Cookie 不按端口隔离；不同路径也不是独立安全边界。新旧使用不同会话 Cookie 名，按部署路径限制作用范围并配置安全属性；会话签名密钥和访问控制独立，不共享旧系统未鉴权入口。Cookie 路径不能代替授权；浏览器规则见 [Cookie 范围](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies) 与 [Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)。
- 进程与目录：独立部署目录、Python 环境或容器、服务名、任务入口、日志与可写数据目录。不得复用旧 cron 标识、flock 文件或覆盖其启动脚本；共享代理若需 reload，先验证配置并保护旧路由。
- 数据：新系统独立数据库/角色或独立 SQLite 文件。可复用已有 PostgreSQL 实例，但不得写旧业务库；迁移与初始化只能作用于新库。备份明确区分两个系统。
- 资源：Q4 压测需考虑同机共存，先隔离环境测量，再在获准窗口以受控流量验证。限制 worker 并发、API 进程/连接池、导出与备份压力，监测旧系统延迟和磁盘空间。共享主机不等于资源隔离或高可用，主机故障会同时影响两套系统。
- 切换：先让新入口独立验收；是否最终将用户转入新入口或替换旧入口另行决策。停用新服务或撤回新路由不删除旧数据；有新库或百度端变更时仍须按 M5/M6 核对恢复。



## 11. 分步实现与验证

按 PLAN 的小步边界实现，不一次生成前后端、数据库、任务与部署全套骨架。先明确本步接口和数据边界，再实现最小必要内容并实际验证。确需多个层支撑一个场景时，按最小可测试纵向链路拆步，不制造无法验证的半成品。

数据库在新库或副本验证；查询先验证权限、映射、粒度和分页，再测性能。外部 API 用可控样本、模拟及故障响应验证幂等、部分失败、超时和重试。页面验证真实交互，不只看截图或构建通过；部署先隔离验证，再按授权同机受控验证。

每步记录实际命令或操作、环境、输入、预期与结果；未执行、受阻或仅模拟的检查明确标注。失败先修复并复测，不以代码生成完成代替验证。
