## 1. 业务与范围

以旧版投放监控看板为参考，保留业务能力，改进性能、交互、可靠性和工程结构。业务是黄金、名表、奢侈品回收的百度搜索获客。完整部门平台仅作背景，CRM、预约到店、小时报、素材生成等不属于本次子系统范围。

历史文档记录“替代人工拓词”的目标；该目标保留，不能仅凭“参考旧版重构”推断其被取消。自动种子、统一队列、直接加词等具体实现是否进入首批，仍须分别确认。

### 4.1 性能路径

server.py:249 的 _query_report_days 已做 GROUP BY，但主要按日期取数；:301 拼合缓存；:355 过滤并二次聚合；:644 汇总；:668 排序和切片分页。默认 7 天明细行数不等于每次接口实际物化的行数。

MappingResolver 在 Python 中解析人员、部门和业务归属，不能只在旧 SQL 尾部添加 LIMIT 就声称结果等价。需先定义映射表、负责人变更的历史口径及聚合粒度，再验证分页和总数。进程级锁与缓存增加协调成本；数据库锁竞争程度需测量，索引是否适配需查询计划确认。

### 4.2 需保留的语义

人工改判不被自动覆盖；有转化与边界词保护；规则保存不自动改历史；规则版本与应用批次可追溯；拉数重复执行不增加重复记录；零分母不伪造成本或率；转化字段原值不丢失。

## 5. 统一口径

综合线索 = 表单(3)+留线索(18)+电话拨通(30)+微信加粉(79)。点咨率 = [一句话(19)+三句话(17)]/点击。线索转化率 = 综合线索/点击。成本 = 消耗/对应转化量，零分母返回空值。

预约/到店与留资不是同一客户批次，不直接相除。对账须统一账户、日期、粒度、过滤、映射版本、回补截止时间和金额精度。金额迁移不得直接从二进制浮点舍入后声称原始金额无损；按可核实源值与精度规则核对。
